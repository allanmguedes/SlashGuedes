# Backup content compatibility

Restoration checks archive integrity and existing input budgets, extracts into an owned transaction folder, applies the local untrusted-history transformation, then validates the staged application content before copying originals or applying any target. Incompatible data produces a localized file-level refusal, without raw parser exceptions/document values. Cancellation and storage errors keep their distinct paths. Rejection creates no fallback/default profile, corrupt-file preservation copy or safety ZIP of a partly restored state.

The contracts are shared with the current readers: Markdown parsing and validation, settings serialization options, usage array/object deserialization and capture-record deserialization/normalization. Restore uses strict mode where tolerant local loaders would return defaults or skip a bad record. It refuses partial invalid records, required settings references set to null, invalid typed properties, duplicate typed members/identities and impossible negative/non-finite counters/dimensions. Dictionary keys remain case-sensitive; uppercase/lowercase accented characters are distinct. Unknown optional properties remain accepted. Existing defaults for absent legacy fields are read in memory; archive bytes are not rewritten to fill them.

Only history file approval is deliberately rewritten. All archive-provided approval fields, including aliases and incompatible values, are discarded first and replaced by a local true flag. Validation does not read any history-referenced file or grant access to it. Settings/snippets/usage bytes remain unchanged. Images/emotes retain existing collection validation and budgets. Schemas 1/2, legacy usage arrays, missing optional preferences and partial archives remain supported; omitted modules are untouched.

This does not repair tolerant/incomplete local reads tracked by #116 or change historical Markdown retention tracked by #119. Durable recovery, protected startup and original preservation remain supplied by #118. Validation is not a signature/authenticity guarantee (#95), and controlled process tests are not physical power-loss certification (#70).

`BackupCompatibilityChecks` runs in the normal smoke suite, using fictitious intact archives with incompatible content and comparing the active set byte-for-byte. `--backup-compatibility-fixtures` in the test executable creates the inert pilot archives and blue PNG. `--backup-compatibility-smoke <output> <fixtures>` in the application uses isolated WPF fixtures (no MainWindow/hooks/devices), checks refusal/layout/focus/accessibility in three languages/two themes and reloads valid content with the real readers. The published executable repeats these tests in CI.
